# 모델 선택

작업 난이도에 맞는 모델을 쓴다. 낮은 난이도에 비싼 모델 쓰지 않고, 판단이 필요한 작업에 싼 모델로 때우지 않는다.

| 난이도 | 예 | 모델 |
|---|---|---|
| 기계적 (탐색, 검색, 파일 위치 찾기) | 파일/함수 위치 찾기, 호출부 나열 | haiku |
| 일반 구현 (스펙 명확, 통합 판단 약간 필요) | 기능 구현, 버그 수정, 여러 파일 조율 | sonnet |
| 설계·아키텍처·복잡한 디버깅 | 구조 결정, 근본원인 분석, 전체 브랜치 리뷰 | opus |

이 플러그인의 `explorer`(haiku) / `implementer`(sonnet) / `architect`(opus) 에이전트는 이 표를 역할로 고정해둔 것. 이름 붙은 에이전트로 안 가고 그때그때 서브에이전트를 띄울 때도(Task/Agent 도구 직접 호출) 같은 기준으로 `model` 파라미터를 명시한다 — 생략하면 세션 기본 모델(보통 제일 비쌈)로 조용히 상속되니 항상 명시한다.

# 코드 리뷰

1. **codex MCP(`/codex:review`)를 우선 사용한다.** rate limit/API 한도로 실패하면 그때만 opus로 직접 리뷰한다 — 실패 원인을 사용자에게 알리고 넘어간다. (이 플러그인의 `/review` 커맨드가 이 흐름을 그대로 구현한다.)
2. **codex든 opus든, 리뷰 결과가 나오면 그 자리에서 바로 타당성을 검토한다.** 결과를 그대로 전달하고 끝내지 않는다.
   - 지적된 파일:라인을 직접 읽어 사실관계를 확인한다.
   - 그 코드의 실제 호출부/소비자가 있는지 확인한다(`grep` 등) — 없으면 잠복 결함, 있으면 실사용 버그로 심각도를 가른다.
   - "지적 맞음/틀림 + 심각도 + 권고(지금 고침/이월)"를 한두 줄로 결론짓는다.
3. `/codex:review` 자체는 review-only 규칙(수정 금지, verbatim 출력)을 그대로 따른다 — 타당성 검토는 그 출력 **다음** 단계로 별도로 한다.

# SDD(subagent-driven-development) 실행 시 효율 조정

`superpowers:subagent-driven-development`로 계획을 실행할 때 다음 3가지를 기본 적용한다 — 토큰/시간 낭비를 줄이기 위함(사용자가 명시적으로 확정한 정책).

1. **리스크 낮은 태스크는 태스크별 리뷰 게이트를 생략한다.** 순수 함수(브리프에 완전한 코드 있음)나 아직 아무도 안 쓰는 고립 신규 파일은 구현만 시키고 리뷰 스킵. 기존 코드를 건드리거나 async/state/통합 지점이 있는 태스크만 리뷰한다 — 실제 버그는 항상 그런 태스크에서만 나왔다(순수함수·고립컴포넌트류는 리뷰해도 지적 0건인 경우가 대부분).
2. **계획이 작고 스펙이 명확하면 SDD 대신 인라인 실행(superpowers:executing-plans)을 먼저 물어본다.** 서브에이전트 격리보다 속도가 중요하고 리스크 낮으면, 매 태스크 새 서브에이전트를 안 띄우고 현재 세션에서 직접 구현하는 쪽이 훨씬 쌈. 자동으로 고르지 말고 계획 규모·리스크를 보고 옵션으로 제시한다.
3. **모든 서브에이전트 디스패치 프롬프트의 Report Format 섹션에 "SendMessage로 보고 필수, idle로 끝내지 마라"를 항상 포함한다.** 안 넣으면 서브에이전트가 리포트 파일만 쓰고 idle로 빠져서, 컨트롤러가 재촉 메시지를 별도로 보내야 하는 왕복이 매번 생긴다.
